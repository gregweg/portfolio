Kubernetes

Deployment / ReplicaSet / Pod

Pod

Pod - Smallest deployable unit in Kubernetes. A Pod contains one or more containers that run together and share networking and storage.

Pod
├── Application container
└── Sidecar container (optional)

Containers inside a Pod share:
- IP address / network namespace
- localhost
- mounted volumes
- lifecycle

ReplicaSet

ReplicaSet - A kubernetes controller that ensures a specified number of identical Pod replicaes are running.

ReplicaSets provide replication and self-healing.

Deployment

Deployment - A higher-level Kubernetes controller that manages ReplicaSets and provides declarative application deployment and rollout behavior.

spec:
  replicas: 3

Deployments also support:
- rolling updates
- rollbacks
- scaling
- rollout history
- declarative application versions

Deployment = release management
ReplicaSet = replica management
Pod        = running workload

Service / Ingress

Service

Service - provides a stable network endpoint for accessing a group of Pods

Client

The Service discovers Pods using labels/selectors.

Common types:

ClusterIP - internal cluster access.
NodePort - exposes a port on each Kubernetes node.
LoadBalancer - asks the cloud provider to provision an external load balancer.

Ingress

Ingress - Defines HTTP/HTTPS routing from outside the cluster to Services inside the cluster.

Internet

Ingress → routes HTTP traffic to Services

Ingress commonly handles:
- hostname routing
- path routing
- TLS termination
- external HTTP/HTTPS traffic

Requests vs Limits

Request

Request - The amount of CPU/memory Kubernetes uses when deciding where a Pod can be scheduled.

resources:
  requests:
    cpu: "500m"
    memory: "512Mi"

Schedule me onto a node that can accomodate this workload.

Limit

Limit - The maximum resource usage Kubernetes allows for a container.

limits:
  cpu: "1"
  memory: "1Gi"

If CPU exceeds the limit:
CPU → throttled

If memory exceeds its effective memory limit:
Memory → container may be OOMKilled

Requests → scheduling / guaranteed allocation assumptions
Limits   → runtime resource ceiling

Poorly chosen values can cause underutilized nodes, throttling, OOMKIlls, or difficult scheduling.

Readiness vs Liveness vs Startup Probes

Readiness Probe

Answers: Can this Pod receive traffic right now?

If readiness fails:

Pod remains running
      ↓
removed from Service endpoints
      ↓
no new traffic

Example: The process is alive, but its dependencies haven't initialized.

Liveness Probe

Answers: Is this application still functioning, or should Kubernetes restart it?

If it repeatedly fails:

liveness failure
      ↓
container restart

Usefull for situations like a process that is alive but deadlocked.
A dangerous liveness probe can create restart loops, so it should test something the applicaiton can reasonably recover from through restart.

Startup Probe

Answers: Has this application finished starting?
Useful for slow-starting applications.

While the startup probe hasn't succeeded, Kubernetes doesn't use the normal liveness behavior to kill the application for simply taking too long to initialize.

Mental Model:

Startup   → Have you started yet?
Readiness → Should I send traffic to you?
Liveness  → Should I restart you?

PDBs - PodDisruptionBudget

PodDisruptionBudget - Specifies how much voluntary disruption an application can tolerate.

Suppose you have:
5 API Pods


A PDB might require:
minAvailable: 4

If Kubernetes maintenance attempts to evict several Pods simultaneously, the PDB helps prevent too many from becoming unavailable.

DPBs primarily protect against voluntary disruptions, such as node drains. They don't magically prevent hardware failures or application crashes.

RBAC - Role-Based Access Control

Controls: Who can perform what action on which Kubernetes resources?

Role
RoleBinding

ClusterRole
ClusterRoleBinding

Role - is namespace-scoped.
ClusterRole can describe cluster-wide permissions or reusable permissions.
The core principle is: Least privilege -- give huands and workloads only the permissions they actually need.

This is especially important for coding/opertations agents.

An incident agent might get:

✓ read logs
✓ inspect Pods
✓ inspect deployments

✗ delete deployments
✗ read unrelated secrets
✗ modify RBAC

node scheduling basics

Kubernetes needs to determeune: Which node should run this Pod?

Pod
 ↓
Scheduler
 ↓
┌────────┬────────┬────────┐
Node A   Node B   Node C

The scheduler considers resource requests plus placement rules and constraints.

nodeSelector =

Run this Pod only on nodes labeled:

gpu=true

Nod Affinity - More expressive placement preferences/requirements. (Node in X availability zone)

Pod Affinity - Place me near Pods matching Z. Useful when workloads benefit from locality.

Pod anti-affinity - Avoid putting me near another instance of myself.
ex)

API Pod → Node A
API Pod → Node B
API Pod → Node C

rather than all replicas on Node A.

Taints and Tolerations
Nodes can effectively say: Don't schedule normal workloads here. A Pod with appropriate toleration is allowed onto that node. Useful for dedicated nodes such as:

GPU nodes
high-memory nodes
specialized workloads

Topology spread constraints
Help distribute replicas across:

nodes
availability zones
other topology domains

Remote State

Terraform needs to remember what infrastructure it manages.

That information lives in: terraform.tfstate

Remote stat eprovides a shared authoritative state representation and supports safer team workflows.

State Locking

Problem:

Engineer A → terraform apply
                    +
Engineer B → terraform apply

Simultaneous changes could corrupt or conflict with infrastructure state. State locking conceptually provides:

Apply A
 ↓
LOCK
 ↓
change infrastructure
 ↓
update state
 ↓
UNLOCK

Then another operation can proceed. Locking behavior depends on the Terraform version/backend and configuration, don't assume every remote-state backend automatically provides identical locking semantics.

Version Pinning

Infrastructure behavior shouldn't unexpectedly change because a provider or mudle updated.
Instead of implicyly taking arbitrary fututre version, constrain versions deliberately.
For example:

terraform {
  required_version = "~> 1.x"

  required_providers {
    google = {
      source  = "hashicorp/google"
      version = "~> 7.0"
    }
  }
}
