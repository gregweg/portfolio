Exploring Patterns for Reliable Systems and Agent Workflows

Today’s notes explore the agent software development lifecycle (SDLC) pattern, reliability strategies, and the unique challenges of running large language model (LLM) workloads on Kubernetes. These topics are essential for ensuring that code changes are well-considered, systems remain reliable under various conditions, and LLMs operate efficiently within a containerized environment.

Part 1 — The agent SDLC pattern

The idea in one line

Move the expensive decisions out of the model's context and into files a human
reviews, so that being wrong is caught at the cheapest point in the cycle.

An agent that is handed a ticket and told "go" makes a hundred small decisions
silently: what the feature actually means, which files to touch, what "done"
looks like, what counts as a regression. Each one is a place to be wrong, and
you find out at the end, in a diff. The pattern splits those decisions into
named artifacts, each one a checkpoint where correction costs minutes instead of
a rewrite.

The loop

intent.md  →  spec.md  →  plan.md  →  implement  →  verify  →  review
   why          what         how        the work    does it    is it
                                                    run?       right?
                                            ↑                     │
                                            └── findings feed back ┘
                                              into CLAUDE.md / skills

Two clocks run at once:

Per-task artifacts — intent.md, spec.md, plan.md. Disposable. Written
for one change, kept alive for that change, then archived with the PR or
deleted. They exist because a context window is lossy: long sessions get
compacted, detail evaporates, and the thing the agent agreed to two hours ago
is no longer in front of it. A file survives compaction. Chat history does not.

Standing artifacts — CLAUDE.md, .claude/skills/, .claude/agents/,
REVIEW.md, the eval suite. Permanent and cumulative. Every correction you
make twice belongs in one of these, or you will make it a third time.

The single most common failure in adopting this pattern is writing the per-task
artifacts and never writing the standing ones. You get good individual changes
and no compounding — the agent is exactly as ignorant on change fifty as it was
on change one.

The per-task artifacts

1. Intent — why

Written by a human, usually not an engineer. Deliberately contains no solution.
Its job is to survive contact with the answer "we should not build this."

# Intent: claims status self-service
Author: J. Ortiz (claims operations). Status: draft.
## Problem
Customers phone the contact center to ask where their claim is.
Handlers spend roughly a third of call time on status-only queries.
## Proposed outcome
Customers see claim status, next step and expected date in the portal.
## Affected users and systems
Claims handlers, portal team, claims-core API.
## Constraints
No new PII in the portal session. Existing authentication only.
## Open questions
Do third-party loss adjusters need access too?

What makes it work: the constraints and open questions. Constraints are the
boundary the agent is not allowed to cross while looking for a clever solution.
Open questions are explicit permission to stop and ask rather than guess — the
agent will otherwise resolve ambiguity silently and confidently.

2. Spec — what

The contract. Observable behavior only: what a user or a caller can see. No
file names, no function names, no implementation. Drafted with the agent from
the intent, then approved by a human — this is the highest-leverage review
in the whole loop, because everything downstream is generated from it.

A spec is good when a test can be written from it without asking a follow-up
question, and when it says what is not being built.

# Spec: claims status self-service (from intent.md 2026-06-02)
Status: approved by J. Ortiz and portal team, 2026-06-05.

## Behavior
A signed-in customer opens a claim in the portal and sees:
- current status, one of: received, in assessment, awaiting documents,
  settled, closed
- the next step, phrased for a customer, not the internal state name
- an expected date for that next step, or "no date yet"

## Acceptance criteria
- A claim in each of the five states renders the correct label and next step.
- A claim with no expected date renders "no date yet" — not an empty cell,
  not today's date.
- A customer requesting a claim they do not own gets 404, not 403.
  (403 confirms the claim exists.)
- When claims-core is unavailable the panel renders from cache with the
  cache age shown; it does not spin indefinitely.
- No field tagged pii in the claims-core schema appears in the portal
  response payload.

## Out of scope
Document upload. Loss adjuster access. Notification of status change.

## Non-functional
- Panel adds no more than 200ms to claim page load at p95.
- Status reads cached 60s per claim; claims-core is rate-limited at
  50 rps shared across the whole portal.

## Open questions resolved
Loss adjusters: no, not in this change. Separate intent if needed.

Note the negative cases (404 not 403, "no date yet" not an empty cell). Those
are the lines that stop an agent from producing something that satisfies the
happy path and quietly leaks or misleads everywhere else.

3. Plan — how

Drafted by the agent from the spec, approved by a human before any code is
written. Short-lived, and short: if the plan is long, the change is too big and
should be split into separate specs.

# Plan: claims status self-service (from spec.md 2026-06-05)

## Files that change
portal/src/claims/StatusPanel.tsx (new), claims-api/routes/status.py,
claims-api/tests/test_status.py

## Order of work
1. Add the status endpoint behind existing auth.
2. Panel against the endpoint.
3. Wire into the portal nav.

## Risks
The claims-core API rate-limits at 50 rps; the panel must cache.

## Proof
test_status.py covers the four claim states; screenshot matches the
approved mock.

The two sections that earn their keep:

  • Files that change. Reviewing this list takes thirty seconds and catches
    the "it decided to refactor the auth middleware" class of surprise before it
    happens, not in a 4,000-line diff.
  • Proof. Stated before the work, so "done" is defined by something other
    than the agent's own judgment at the end of a long session. Without it you
    get "I've implemented the feature and it should work now."

During implementation the plan is the agent's working memory. Have it tick off
steps in the file as it goes — after a compaction the file is what tells it
where it was.

4. Implement

The plan is worked one step at a time, not all at once. Each step should end
somewhere the tests pass, so a bad step is one revert rather than an
archaeology session.

5. Verify — does it actually run?

The step people skip, and the one that separates a pattern that works from a
pattern that produces confident, broken changes. Tests passing is not the same
as the feature working; an agent that wrote both the code and the test has
correlated errors in them.

Verification goes to a subagent with its own context window — something that
did not write the code and is not invested in it.

.claude/agents/verifier.md:

---
name: verifier
description: Runs the app and checks the change works before the session
  reports done
tools: Bash, Read
---

Start the app with make run. Exercise the changed behavior and the two
nearest neighboring flows. Report what you ran, what you saw, and any
behavior that does not match spec.md. Do not fix anything; report only.

Three details do the work here:

  • tools: Bash, Read — no Edit. It structurally cannot paper over what it
    finds.
  • "Do not fix anything; report only." A verifier that fixes destroys the
    signal. You want the list of what was wrong, not a silently repaired diff.
  • "the two nearest neighboring flows." Regressions live next door to the
    change, not in it.

6. Review

Review with written instructions, not vibes. The point of REVIEW.md is
severity calibration: a review where everything is Important is a review nobody
reads.

REVIEW.md:

# Review instructions
## Passes
Run three passes and tag each finding with its pass:
- Bugs: logic errors, broken edge cases, subtle regressions
- Security: injection risks, authentication gaps, PII in logs
- Compliance: the change matches spec.md, plan.md and our design principles
## What Important means here
Reserve Important for findings that would break behavior, leak data
or breach a policy. Style and naming are nits.
## Cap the nits
Report at most five nits per review; summarize the rest as a count.
## Do not report
Generated files under src/gen/ and anything CI already enforces.

Separate passes matter because a single pass optimizes for whatever it noticed
first — usually style, which is the cheapest thing to see and the least
valuable thing to report.

The feedback edge

The loop closes when review findings go into the standing artifacts rather than
into a PR comment. "It keeps using double for money" is a CLAUDE.md line,
written once. A PR comment fixes one PR.

The standing artifacts

CLAUDE.md — the always-loaded context

# Payments service
## Commands
- Build: make build
- Test: make test (unit), make itest (integration, needs docker)
- Lint: make lint (runs in CI; fix before pushing)
## Conventions
- Java 21, Spring Boot 3. No new Lombok.
- Money is always BigDecimal, never double.
- Every endpoint needs an integration test in src/itest.
## Architecture
- api/ holds REST controllers, core/ holds domain logic,
  adapters/ talks to external systems.
- Kafka events are defined in schemas/; never edit generated classes.
## Things Claude gets wrong
- Do not bump dependency versions; the platform team owns them.
- The legacy v1/ package is frozen; changes go in v2/.

This is loaded on every session, so every line costs tokens on every turn.
Keep it under roughly a page. Rules of thumb:

  • Commands first. Knowing the test command is worth more than any amount of
    architectural prose, because it's what lets the agent close its own loop.
  • State conventions as rules, not preferences. "Money is always BigDecimal,
    never double" is followable. "We prefer good numeric hygiene" is not.
  • "Things Claude gets wrong" is the highest-value section. It is the
    accumulated diff between what the model assumes and what is true here, and
    it's the section that should grow. Everything else is mostly static.
  • Anything long, conditional, or needed only sometimes belongs in a skill, not
    here.

Skills — loaded on demand

.claude/skills/secure-api-review/SKILL.md:

---
name: secure-api-review
description: Apply the API security standard. Use whenever creating or
  modifying an external-facing endpoint, reviewing API code, or
  generating an OpenAPI spec.
---
# Secure API review
When you create or change an API endpoint:
1. Authentication: every endpoint requires the gateway JWT;
   no anonymous routes outside /health.
2. Input validation: validate request bodies against the OpenAPI
   schema and reject unknown fields.
3. Audit: every state-changing endpoint emits an audit event with
   actor, action, entity and timestamp.
4. Data classification: fields tagged pii in the schema must never
   appear in logs or error messages.
Run scripts/check-endpoints.sh and include its output in your summary.

Only the name and description sit in context until the skill fires — the body
loads when the description matches. So:

  • The description is the trigger, and it is the whole ballgame. Write it in
    terms of when to use this, not what it is. "Apply the API security
    standard" alone would rarely fire; the "Use whenever…" clause is what makes
    it match. A skill that never triggers is worth exactly nothing.
  • Terminate in a command. scripts/check-endpoints.sh turns a checklist
    the agent can claim to have followed into a result it has to show. Anything
    mechanically checkable should be a script the skill runs, not a numbered
    instruction.
  • A skill is also the natural home for the standards that don't fit in a
    review — the ones that need to be applied while writing, not after.

Evals — regression tests for the setup itself

CLAUDE.md and .claude/ are code, and they regress: someone adds a rule that
contradicts another, a skill description drifts until it stops firing, a
convention is removed and nobody notices for two months. The eval suite is the
test for that, pinned to the paths it covers.

.github/workflows/agent-evals.yml:

name: Agent evals
on:
  pull_request:
    paths: ['CLAUDE.md', '.claude/**']
  schedule:
    - cron: '0 2 * * *'
jobs:
  evals:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm install -g @anthropic-ai/claude-code
      - name: Run eval suite
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |
          for eval in evals/*.json; do
            claude -p "$(jq -r '.prompt' $eval)" \
              --allowedTools "Read,Edit,Bash(make test)" \
              --output-format json > result.json
            ./evals/check.sh "$eval" result.json
          done
  • paths: triggers the suite exactly when the agent's configuration changes —
    the one moment a regression can be introduced.
  • The nightly schedule: catches drift that isn't caused by your commits:
    model updates, dependency changes, external services moving.
  • --allowedTools is doing real work. It bounds what a run can do in CI, and
    it makes the eval a test of judgment under constraint rather than a test of
    whether the agent can find some way through.
  • Good evals are behavioral, not textual. "Does it use BigDecimal when adding a
    money field" beats "does the output mention BigDecimal."

What each artifact prevents

Artifact Answers Written by Lifetime Failure it prevents
intent.md Why Requester (human) One change Building the wrong thing well
spec.md What Agent, approved by human One change Ambiguity resolved silently and wrongly
plan.md How Agent, approved by human One change Surprise blast radius; "done" self-declared
CLAUDE.md Always-true context Team, accumulates Permanent Re-explaining the same conventions forever
Skills Conditional standards Team, accumulates Permanent Standards applied inconsistently or not at all
Subagents Independent checks Team Permanent Author grading its own work; context flooding
REVIEW.md Severity calibration Team Permanent Reviews of uniform, ignorable urgency
Evals Does the setup still work Team Permanent Silent config drift

Adoption notes

  • The gate is human approval, not the file. An artifact nobody reads is
    ceremony. If you're approving specs without reading them, delete the step and
    admit what you're doing.
  • Start with CLAUDE.md and the verifier. Commands plus "run it and report"
    is most of the value for two files of effort. Everything else is refinement.
  • Scale the ceremony to the change. A one-line fix does not need an intent
    doc. The pattern earns its cost when the change is large enough that being
    wrong is expensive, or when several people have to agree on what "right"
    means.
  • Watch for spec inflation. Specs that grow implementation detail have
    become plans, and the human approval on them starts costing more than it
    returns.
  • The artifacts are for humans too. A spec that makes an agent's output
    predictable makes a new team member's output predictable for the same reason.

Part 2 — Reliability

A reliable system can perform its function, tolerate errors, and prevent
unauthorized access or abuse. Reliability implies availability but is more than
that: building for reliability means added security, error-handling, disaster
recovery and countless other contingencies.

Two classes of error

  • Hardware errors — network outages, server failure. These won't be fixed
    quickly and are often called non-transient errors.
  • Application errors — bugs, failures to accommodate spikes in traffic.
    These should resolve quickly and are known as transient errors.

Retries

An application detecting a failure will immediately retry. This may work fine if
the failure is unusual and unlikely to repeat, but for common transient failures
(e.g. network failures) repeat retries may overload the downstream system once
the underlying issue is resolved.

Delayed retry holds the retry back for a set amount of time, allowing the
system to recover. An exponential backoff strategy systematically decreases
the rate of re-transmission in search of an acceptable retry rate.

To avoid retries building up in high-traffic systems and causing a high system
load once the error clears — the thundering herd problem, which can cause
more damage than the original transient error as your resources struggle with
the request volume — introduce jitter, randomness in the delay interval, so
clients don't synchronize.

Circuit breakers

A robust retry alleviates short-lived transient errors. But what about
non-transient errors, or transient errors with uncertain recovery times?

The circuit breaker pattern accepts failure and stops the application from
repeatedly trying to execute. This prevents cascading failures and saves
computing power.

State Behavior Transition
Closed Requests pass through; failures counted Failures exceed threshold within an interval → Open
Open No requests let through; timer running Timer expires → Half-open
Half-open A few test requests allowed through All succeed → Closed, counter reset. Any fail → Open, timer restarts

Saga pattern

Saga is a strategy used most often in microservice architecture, where
completing an action (a distributed transaction) entails successfully
completing a set of local transactions across multiple independent services.

Instead of a single distributed transaction, the component local transactions
are decoupled, grouped and executed sequentially. Each string of related local
transactions is a saga.

If the saga coordinator detects a failure it invokes a predefined set of
countermeasures, effectively reversing the actions already taken. On an
e-commerce site, the inventory number would revert to its previous state, and
payment and cart updates would be reversed.

Two ways to implement it:

  • Choreography — decentralized; each local transaction triggers the next.
  • Orchestration — a centralized controller directs saga participants.

Part 3 — LLM and agent workloads on Kubernetes

What's different about running LLM and agent workloads versus a normal service?
Four assumptions break:

  • capacity isn't CPU
  • requests aren't cheap or idempotent
  • connections are long-lived
  • health checks can't see the failure that matters
Assumption Why it breaks What you do instead
Scale on CPU Capacity is tokens/min and concurrent requests; a waiting pod is idle KEDA on queue depth or in-flight requests, not HPA on CPU
Retries are free Every retry spends money and provider quota; many calls aren't idempotent Retry budgets, circuit breakers, idempotency keys, per-request spend caps
Rolling updates are safe Streaming connections get cut mid-response; agent runs can last minutes Long termination grace, connection draining, or checkpointed/durable runs
Probes detect failure A model returning fast nonsense is HTTP 200 Golden-set canaries in prod as a quality signal alongside liveness
Cost is finance's problem A runaway agent loop burns budget in minutes Per-tenant and per-agent budgets with kill switches; treat spend as a paged alert
