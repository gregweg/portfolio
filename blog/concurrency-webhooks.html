Concurrency, Parallelism, Multithreading & High-Throughput Webhook Processing

Today's exploration dives into the nuanced differences between concurrency, parallelism, and multithreading. It also tackles the architectural challenges of building a high-throughput webhook processor capable of handling millions of incoming messages per second without dropping packets or violating strict ordering rules within user sessions.

Concurrency vs Parallelism vs Multithreading

Concurrency (Dealing with multiple tasks)

A single processing core rapidly switches( context switches) between tasks so that each tasks makes progress without waiting for others to finish.

Concurrency: A single barista taking orders from three diffent custoemrs. They take one order, start brewing the cofee, quickly take the next order, continue until done.

Parallelism (Doing multiple tasks simultaneously)

Multi-core processors, tasks are literally running at the same microsecond on separate processing units. Used for CPU-bound operations such as heavy data processing, image rendering or scientific simulations.

Parallelism: Three braista working at three different espresso machines, making three coffees at the exact same time.

Multithreading (The Tool)

Single-core machine, multithreading achieves concurrency because the processor interleaves the execution of threads. On a multi-core machine, multithreading can achieve parallelism because the OS can assign different threads to different cores.

Multithreading: The overal system of having a single kitchen workspace (the process) with multiple people (threads) cooperating to get the job done faster.

System Design: High-Throughput Webhook Processor (The Meta API Ingestion)

Webhook - lightweight, event-driven mechanism that allows one application to send real-time data to another application as soon as a specific event occurs. A reverse API calling or automated notification between servers.

Anatomy of a Webhook Request:
- A Target URL: A public endpoint exposed by the receiving application.
- An HTTP Method: Almost always a POST request, as it is pushing new data to your server.
- Headers: Often contains authorization tokens or cryptographic signatures (like an X-Hub-Signature) so the receiver can verify that the data actually came from a trusted source (like Meta or Stripe) and not a random hacker.
- A Payload (Body): The actual data being delivered, typically structured as JSON.

Common Use Cases
- Payment Gateways: Stripe uses webhooks to notify your server the exact milisecond a customer's credit card payment clears or fails.
- E-commerce: Shopify uses webhooks to tell your inventory app that an item was just purchased.
- CI/CD Pipelines: GitHub uses webhooks to trigger an automated deployment system whenever a developer pushes new code to a repository.

System/WhatsApp context
1. The Event: A customer sends a WhatsApp message to a retailer's business phone number.
2. The Trigger: Meta's servers receive that message and immediately look up the webhook URL that we registered for that specific business acount.
3. The Payload: Meta wraps up the details of the message (the text, the sender's phone number, the timestamp) into an HTTP POST request, usually formatted as JSON.
4. The Delivery: Meta acts like a browser makinga web request, firing an asynchronous HTTP POST directly to our public URL (https://api.mysite.ai/v1/webhooks/whatsapp)
5. The Acknowledgement: Server receives the payload, verifies it, and instantly replies with an HTTP 200 OK status code to let Meta know the message was successfully received.

The Challenge: How to ingest millions of incoming messages per second without dropping packets, ensuring strict ordering per user session, and handling sudden traffic bursts.

What to focus on:

Decoupling with Kafka: Using a lightweight API gateway/ingestion layer that instantly drops incoming webhooks into a Kafka topic to guarantee durability and shield downstream services.

Partitioning Keys: Discussing how you would partition Kafka topics (e.g., partitioning by user_id or phone_number) to ensure messages from the same chat session are processed sequentially while maintaining horizontal scalability across workers.

Idempotency: WhatsApp can retry webhook deliveries. You'll need an idempotency layer (using a fast key-value store or DynamoDB conditional writes) to ensure a single incoming message isn't processed or answered twice.

Core Entities

  • Business Account (WABA): Retailer owning their own WhatsApp number
  • Customer / Contact: The unique individual messaging the business.
  • Session: An active conversational window (often 24 hrs based on WhatsApp's billing logic)
  • Message: Single immutable event (inbound/outbound)

Storage Schema Design:

DynamoDB for fast, high-volume idempotency checks and active session tracking
Postgres for complex relational data (business metadata, structured order tracking)

A. Idempotency Layer (DynamoDB)
Before processing a message, we must check if Meta has sent it before. We use DynamoDB for its predictable sub-10ms single-key writes and automatic data eviction.

DynamoDB processes ConditionExpression writes atomically at the database engine partition level. If two identical WAMIDs arrive at the same time, one will succeed and the other will fail the condition check, guaranteeing absolute deduplication accuracy without locking application databases.

Step-by-Step Deduplication Flow
1. Pulling from Queue: The Python worker pulls a batch of events from its assigned Kafka partition.
2. Extracting the Token: The worker extracts the id (WAMID.ABGG...) from the message payload.
3. The Atomic Check (DynamoDB): The worker executes a PutItem operation to the whatsapp_processed_messages DynamoDB table with a Condition Expression.

Table Name: whatsapp_processed_messages

Partition Key (PK): message_id (The unique WAMID string supplied by Meta)

Attributes:

status: (e.g., PROCESSING, COMPLETED)

ttl: Unix timestamp (set to 7 days in the future). DynamoDB will automatically drop this row after a week to keep storage costs zero.

B. Conversational State & Messages (DynamoDB)
Because conversational text flows are high-velocity key-value patterns, keeping active sessions in DynamoDB prevents Postgres connection pools from locking up during a marketing blast.

Table Name: whatsapp_chats

Partition Key (PK): waba_id#customer_phone (Combines the business account and customer number)

Sort Key (SK): entity_type#id (Allows storing both session metadata and individual messages in the same table for single-query retrieval via a begins_with condition)

Partitioning Keys: Discussing how you would partition Kafka topics (e.g., partitioning by user_id or phone_number) to ensure messages from the same chat session are processed sequentially while maintaining horizontal scalability across workers.

Idempotency: WhatsApp can retry webhook deliveries. You'll need an idempotency layer (using a fast key-value store or DynamoDB conditional writes) to ensure a single incoming message isn't processed or answered twice.

  1. Ingress: Meta hits /v1/webhooks/whatsapp
    API Gateway checks the payload signature, extracts the waba_id drops the raw JSON into KAfka on a topic named whatsapp.inbound.raw. The mesagges key is set to the customer's phone number (1234567890) to ensure all messages from this consumer end up on the exact same Kafka partition, guaranteeing chronological order.

  2. Ingress Returns: The API immediately gives Meta a 200 OK

  3. Worker Processing: A python worker cluster consumes from kafka.

  4. Deduplication: The worker attempts a conditional write into the DynamoDB Idempotency table using the message_id. If the item already exists, the worker safely drops the duplicate message.

  5. State Mutation: The worker reads/updates the active state row (SESSION#SESS_999) in the second DynamoDB table, appends the new message event, and determines whether to pass this task to the LLM agent pipeline or route it to a human agent queue.

Semantic Partitioning

API layer pushes the event to Kafka, it defines a specific Partition Key

customer_phone_number or waba_id + customer_phone_number

Hash(key) (mod N) where N is the number of partitions, because the phone number is identical for both messages, they are guaranteed to land on the exact same partition

A single Kafka consumer stream handles that partition sequentially. Message #2 will sit safely in th equeue until the worker completely finishes processing and committing message #1.

API Gateway Integration - Most modern API Gateways can perform a direct service integration with Kafka without qa custome compute layer sitting in the middle.

[Meta Webhook] ---> [AWS API Gateway] ---> [Kafka Topic] ---> (200 OK to Meta)

  1. Verification & Ingestion: API Gateway acts as the public reverse proxy. It receives HTTPS POST request from Meta.

  2. Direct Proxying: Gateway is configured to automatically parse the inbound header, validate the Meta signature and forward the payload directly to the Kafka HTTP Bridge or cluster.

  3. Immediate Acknowledgement: The gateway receives the acknowledgement from Kafka that the write was durable, and immediately fires back a 200 OK to Meta. This keeps your API layer entirely stateless, CPU-light, and capable of handling tens of thousands of requests per second out-of-the-box.
