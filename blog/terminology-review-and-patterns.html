Day in the Life of Client-Side & Backend Terminology

In today’s notes, Greg delves into the intricacies of client-side terminology like optimistic updates, background sync, and IndexedDB, alongside backend concepts such as idempotency and rate-limiting. The discussion is grounded in practical examples and trade-offs relevant to real-world system design.

Terminology Review

Client Side Terminology

Optimistic Updates

Definition: Updating the client UI immediately after a user action before receiving confirmation from the server, assuming the network request will succeed.

Key Use Case: Low-latency UI responsiveness (toggling a "Like" button, sending a chat message).

Trade-off / Gotcha: Requires robust rollback logic and error handling if the server request fails or returns a validation error.

Background Sync

Definition: A browser/application strategy that defers network requests until stable connectivty is restored, executing them in the background (often via Service Workers)

Key Use Case: Offline-first mobile/web applications (ex. queuing draft emails or field data logs).

Trade-Off / Gotcha: Requests can be delayed unpredictably; requires handling out-of-order state updates when reconnecting.

IndexedDB/SQLite

Definition: Persistent, client-side transactional databases (IndexedDB natively in browsers, SQLite via WASM or mobile wrappers) for storing structured data locally.

Key Use Case: Caching complex application state, enabling offline functionality, and reducing API reads for large datasets.

Trade-Off / Gotcha: Schema migrations on client devices are complex, and storage limits vary across platforms.

Payload Compression

Definition: Reducing the byte size of requests/response payloads using algorithms like Gzip, Brotli, or binary serialization formats (e.g., Protocol Buffers)

Key Use Case: Minimizing network bandwidth usage and latency over slow or constrained mobile networks.

Trade-Off / Gotcha: Adds CPU overhead for encoding/decoding on both client and server; negligible gain on very small JSON payloads.

API/Backend Terminology

Idempotency

Definition: A property of an API endpoint where making the exact same request multiple times yields the same system state as making it once.

Key Use Case: Preventing duplicate charges or creations during network timeouts/retries via Idempotency-Key headers.

Trade-Off / Gotcha: Requires caching request keys and response in a fast distributed store (e.g., Redis) with explicit expiration TTLs.

Rate-Limiting (Tocken Bucket)

Definition: An algorithm that tracks available requests as "tokens" in a bucket filled at a constant rate; requests consume tokens and are rejected (HTTP 429) when the bucket is empty.

Key Use Case: Protecting endpoints from denial-of-service, scraping or resource exhaustion while permitting controlled traffic bursts.

Trade-Off / Gotcha: Need distributed state (e.g., Redis scripts) to enforce limits accurately across multiple API instances.

API Gateway

Definition: A single entry-point reverse proxy that handles cross-cutting concerns like routing, authentication, SSL termination, and rate-limiting before forwarding requests to microservices.

Key Use Case: Centralizing edge security and routing logic away from individual downstream services.

Trade-Off / Gotcha: Can become a single point of failure and a performance bottleneck if over-packed with heavy business logic.

Stateless Auth (JWT/OAuth2)

Definition: An authentication model where user identity and permissions are embedded inside a cryptographically signed token (JWT), eliminating server-side session lookups.

Key Use Case: Scaling authentication horizontally across stateless microservices.

Trade-Off / Gotcha: Revoking tokens before they expire is difficult without maintaining an explicit invalidation list (blocklist).

Data/Queue

Read-heavy caching

Definition: Placing an in-memory datastore (e.g., Redis, Memcached) in front of the primary database using patterns like Cache-Aside or Read-Through to serve frequent reads.

Key Use Case: Systems with high read-to-write ratios (e.g., user profiles, product catalogs).

Trade-Off / Gotcha: Invalidation is notoriously difficult; risks serving stale data or causing "cache stampedes" on cold cache misses.

Message Brokers

Definition: Middleware (e.g., RabbitMQ, Apache Kafka, AWS SQS) that decouples producers and consumers by asynchronously routing, queuing, and delivering messages.

Key Use Case: Aynchronous task processing, event-driven architectures, and smoothing out traffic spikes.

Trade-Off / Gotcha: Introduces eventual consistency, message ordering challenges, and poison-pill handling requirements.

Worker Pools

Definition: A concurrency pattern where a fixed number of reusable threads or processes consume tasks from a shared queue.

Key Use Case: Preventing CPU/memory exhausion by bounding resourc eonsumption when handling heavy background workloads

Trade-Off / Gotcha: If the pool size is too small, tasks back up in the queue; if too large, context switching degrades throughput

Database Sharding/Partitioning

Definition:
- Partitioning: Splitting a larger table into smaller sub-tables within a single database instance (e.g., by date range)
- Sharding: Distributing data across multiple separate databases instances using a shard key (e.g., user_id % num_shards consistent hashing)

Key Use Case: Overcoming storage and CPU/IOPS limits of a single databse machine when scaling horizontally.

Trade-Off / Gotcha: Cross-shard joins, distributed transactions, and re-sharding existing data add significant operational complexity.

Problem Triggers -> Pattern/Tool + Tradeoffs

Handling High Traffic & Scaling

High Read-to-Write Ratio (e.g., 99% reads, 1% writes like Twitter feeds)

Pattern / Tool: Cache-Aside / Read Replicas

Why Use It?: Offloads reads from primary DB; drastically reduces query latency.

Tradeoffs & Gotchas:
- Cache Invalidation: Complex logic to prevent stale reads.
- Replication Lag: Replicas may serve slightly outdated data.

Monolithic DB hitting disk/CPU limits on Writes

Pattern / Tool: Database Sharding (Horizontal Paritioning)

Why Use It?: Distributes write load across multiple hardware nodes.

Tradeoffs & Gotchas:
- Cross-Shard Joins: Extremely slow or unsupported.
- Hotspot Shards: Poor choice of shard key leads to uneven load

Sudden Traffic Spikes / Burstiness (e.g. flash sales, ticket booking)

Pattern / Tool: Message Queue / Asynchronous Buffer

Why Use It?: Smooths out traffic spikes ("load leveling") so downstream workers aren't overwhelmed.

Tradeoffs & Gotchas:
- Eventual Consistency: User doesn't get an immediate confirmation.
- Queue Management: Must handle dead-letter queues (DLQs) for failed processing.

Global User Base / High Network Latency

Pattern / Tool: CDN (Content Delivery Network) & Anycast Routing

Why Use It?: Serves static assets and dynamic content closer to the edge via PoPs (Points of Presence).

Tradeoffs & Gotchas:
- Cost: High egress charges.
- Purging Cache: Invalidation across globally distributed edge nodes takes time.

Real-Time Communication & APIs

Bidirectional, Low-Latency Updates (e.g., chat apps, collaborative editors, gaming)

Pattern / Tool: WebSockets

Why Use It?: Full-duplex persistent connection over a single TCP connection.

Tradeoffs & Gotchas:
- Stateful Servers: Makes horizontal scaling and load balancing complex (requires stick sessions or a pub/sub backbone)

Server-to-Client Updates Only

Pattern / Tool: Server-Sent Events (SSE)

Why Use It?: Lighter than WebSockets; built on HTTP, automatic reconnection out of the box.

Tradeoffs & Gotchas:
- Unidirectional: Connection is read-only for the client; sending data requires sepearate HTTP POST requests.

Protecting Downstream Services from Overload

Pattern / Tool: API Gateway + Rate Limiter

Why Use It?: Centralizes Auth, SSL termination, routing and prevents abuse/DDoS.

Tradeoffs & Gotchas:
- Single Point of Failure (SPOF): If the gateway goes down, all API traffic fails.
- Added Latency: Every request incurs extra hop latency

Consistency & Distributed Data

Financial / Ledger Transactions across Microservices

Pattern / Tool: Saga Pattern (Orchestration vs Choreography)

Why Use It?: Manages long-running distributed transactions without locking tables across DBs via compensating actions.

Tradeoffs & Gotchas:
- Complex Rollbacks: Writing reversing/compensating logic for every step is error-prone
- Eventual Consistency: Intermediate states are visible to users.

High Read Throughput + COmplex Analytical Queries

Pattern / Tool: CQRS (Command Query Responsibility Segregation)

Why Use It?: Decouples reads and write data models, optimizing each independently

Tradeoffs & Gotchas:
- Code Duplication: Requires maintaining distinct schema and models.
- Data Lag: Read side is eventually consisten with the write side.

Complete Audit Trails / Un-deleteable History (e.g., bank accounts, inventory logs)

Pattern / Tool: Event Sourcing

Why Use It?: Appends state changes as imutable events rather than mutating current state.

Tradeoffs & Gotchas:
- Schema Evolution: Changing event formats over time is difficult.
- Replay Latency: Rebuilding current state from scratch requires creating periodic snapshots.

Reliability & Fault Tolerance

Preventing Cascading Failures (e.g., slow third-party payment vendor)

Pattern / Tool: Circuit Breaker Pattern

Why Use It?: Fast-fails requests to a failing service to give it time to recover, keeping the rest of the app functional.

Tradeoffs & Gotchas:
- Degraded User Experience: Must design fallback UI states.
- Tuning Thresholds: Setting error rates and sleep windows accurately requires precise telemetry.

Idempotent Operations over Unreliable Network

Pattern / Tool: Idempotency Keys

Why Use It?: Allows clients to safely retry failed HTTP requests (like payments) without double-processing.

Tradeoffs & Gotchas:
- Storage Overhead: Must store idempotency tokens and past responses in distributed memory. (e.g., Redis TTLs).

Zero Downtime Deployments

Pattern / Tool: Blue/Green or Canary Deployments

Why Use It?: Routes traffic progressible to test new releases safely with instantaneous rollback capability.

Tradeoffs & Gotchas:
- Cost: Blue/Green requires running duplicate hardware environments during releases.
- DB Migrations: DB schemas must remain backward-compatible with both old and new app versions simultaneously.

The Transactional Outbox Pattern: To guarantee that an event is 100% produced whenever the DB write succeeds, write an event into the database within the same database transaction.

  1. Transaction Begin:
    • Insert into leads table.
    • Insert an event record into an outbox table ( outbox: { id, event_type: "lead.created", payload, status: "pending" })

  2. Transaction Commit.

  3. A separate lightweight worker process continuously polls or tail-reads outbox table and pushes those pending rows straight into RabbitMQ/SQS/Kafka, updating their status to published.

  4. Pros: Guarantees at-least-once delivery and zero event loss without needing complex infrastructure changes.

  5. Cons: Requires a polling worker or log scanner on the outbox table.

How do we bridge the message queue events over to WebSockets or SSE so the Enterprie Admin's dashboard updates instantly?

Main API nodes and workers are stateless, admin's browser holds an open WebSocket connection with Server Node A, while sale's rep's phone might hit Server Node B.

Need a pub/sub backbone to bridge that gap.

3-Step Connection Pipeline

1. The Pub/Sub Router (Redis)

  • When background worker consumes a lead.created event from SQS/Kafka, it immediately puiblishes that payload to an in-memory Pub/Sub channel (Redis Pub/Sub) keyed by thte Enterprise Team ID:
  • Channel Name: team:tenant_123:events
  • Payload: { event: "LEAD_CREATED", rep: "Alex", time: "10:03AM", stats: { totalToday: 142 } }

Message queues like SQS are meant for worker task distribution (one worker processes one message).
Predis Pub/Suc is meant foor broadcasting - it instantly fans out a single message to dozens of listening API/WebSocket server instances in sub-millisecond time.

2. Connection Management & Gateway Nodes

  • When the Enterprise Admin logs in, their browser opens a persistent Server-Sent Events (SSE) connection to a Gateway node (or a dedicated real-time service like Socket.io / AWS API Gateway WebSockets)
    1. Authentication: Authenticate the connection via a short-lived token (JWT) passed in query params or headers during the handshake.
    2. Subscription: The node registers interest in the team's Redis channel (SUBSCRIBE team:tenant_123:events)
    3. Push to Client: Whenever Redis broadcasts an event on that channel, the Node server receives it in-memory and pushes it down the matching client's socket

SSE Persistent Connection Pipeline

SSE uses a standard HTTP/1.1 or HTTP/2 GET requests with continuous streaming response headers:

GET /api/v1/teams/tenant_123/live-stream HTTP/1.1
Host: api.popl.co
Authorization: Bearer <jwt_token>
Accept: text/event-stream

The Wired Data Format

When Redis Pub/Sub receives an event, the Edge API server formats the JSON into plain text liens starting with data: and separated by double new lines (\n\n):

id: evt_987654321
event: lead_captured
data: {"rep": "Alex", "lead": "Acme Corp", "total_today": 142}

id: evt_987654322
event: leaderboard_update
data: {"top_rep": "Sarah", "scans": 38}

Client-Side Implementation (Standard Browser API)
While WebSockets require managing manaual reconnect loops and heartbeat intervals, SSE uses the browser's native EventSource API, which manages network drop-outs automatically:

// Native browser API — no external libraries needed
const eventSource = new EventSource('/api/v1/teams/tenant_123/live-stream');

// Listen for custom events pushed from the server
eventSource.addEventListener('lead_captured', (event) => {
  const data = JSON.parse(event.data);
  updateDashboardFeed(data);
});

// Auto-reconnect with historical catch-up built-in
eventSource.onerror = (err) => {
  console.log('Connection lost, browser is auto-reconnecting...');
};

Why SSE over WebSockets
- Lower Operational Overhead: Works out-of-the box with standard HTTP/2 multiplexing, ALB/Ngninx load balancers, and Cloudflare/Fastly proxies without requiring specialized WebSocket connection upgrading logic.
- Resilience at Conferences: Corporate event Wi-Fi frequently drops. SSE automatically sends a Last-Event-ID header upon reconnecting, allowing your Edge server to replay missed Redis events without custom client-side retry engines.
- Simplicity: Unidirectional (Server -> Client) fits a dashboard feed perfectly. You avoid the overhead of managing full-duplex framing when the client never needs to push raw data back down the socket.

How SSE Keeps the Connection Open
Under the hood, SSE leverages standard HTTP streaming:
1. Initial Request: The client sends an HTTP GET reques tot an endpoint (/api/v1/live-leads)
2. Infinite Headers: The server responds with 200 OK, Content-Type: text/event-stream, and Connection: keep-alive.
3. Chunked Streaming: Instead of sending a Content-Length header and closing response (like a normal REST API), the server leaves the HTTP response stream open indefinitely.
4. Pushing Data: Whenever an event happens ont he backend (a Redis Pub/Sub message fires), the server writes a chunk of text directly down that open HTTP socket.

4. Edge Cases & System Failure Scenarios

Network drop mid-sync: Use idempotency keys (UUID generated on the client) so retried requests don't create duplicate leads.

External API Failure (ex. Salesforce rate limit / down): Implement exponential backoff retries with Dead Letter Queues (DLQ) for manual reply or alerted retries

Thundering Herd / Cache Stampede: If a viral profile gets thousands of hits at once, use stale-while-revalidate or edge caching.
